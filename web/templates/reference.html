What this dashboard is

It records what cq executed
Queue lifecycle events are written to a local store as they happen. That history survives restarts; the live panels on the overview do not, because they are read from the running process on each request.
Failures are not a dead-letter queue
If something feeds cq — SQS, a database poller, any transport — that system owns the dead-letter queue and the redrive. The failures page shows the cq executions that led there: the attempts, the errors, the timings.
In flight understates real backlog
cq only knows about work already pulled into memory. Messages still waiting on a transport are invisible here. This answers "what is this process doing", not "how much work exists".
Dropped events mean incomplete history
The recorder hands events to a buffered writer and never blocks a worker. If that buffer fills, events are dropped and counted rather than slowing the queue. A non-zero dropped count on the overview means history has gaps.
{{if .Controls}}
Controls are limited to reversible actions
Pause, resume, and worker scaling only. Stopping and draining are not offered: a stopped cq queue cannot be restarted in-process, so that belongs in a deployment tool. Every attempt, including rejected ones, is audited.
